## 1. 总体要求

- 用第一人称写，像在跟人讲事情。不要"本文将从……展开""接下来我们来看""综上所述"这类播报腔。
- 不夸张、不标题党，不为了吸引注意故意拔高。
- 一个点说完就直接进下一个点，中间不要插过渡性的总结或回指。
- 小节标题用短标签或短问句，不要把一整句话当标题。
- 术语和事实优先。纯装饰的句子直接删。

---

## 2. 禁止出现的句式

以下每一条都是作者明确纠正过的，写完必须自查。

### 2.1 「不 X，也不 Y」这类排比

> ✗ 对象创建完就静静待着，不执行、不推理，也不调用任何函数。
> ✓ 对象创建完之后就一直放在那里，等 Swarm 来读。

> ✗ 它不会说「这任务简单，换个便宜的」，也不会说「这任务复杂，升到 GPT-4」。
> ✓ Swarm 把 `agent.model` 直接填进请求里，中间没有挑选的动作。

### 2.2 拿比喻当句子主干或结论

> ✗ AI 模型只是它借用的「大脑」。
> ✓ AI 模型是它调用的推理引擎。

> ✗ 它是一张等着被查询的配置表。
> ✓ 它的作用就是把配置存住。

> ✗ LangChain 的 Memory 是「存东西的地方」，Swarm 的 Context Variables 是「传东西的管子」。
> ✓ 直接写两边各自关心什么，不做比喻映射。

> ✗ 它是个空箱子。
> ✓ 里面放什么完全由你和你的函数决定。

展开讲的类比可以有（例如第二章里的「寄快递」），但不要压缩成一句话当结论。

### 2.3 「关键在于：…… 它只 ……，而不是 ……」这种强调加转折的套路

> ✗ 关键在于：AI 模型看不到「会转到哪个 Agent」。它只看到这个函数的名字和文档字符串，它决定的是调不调，而不是调了之后去哪。
> ✓ AI 模型看不到「会转到哪个 Agent」。它能看到的只是这个函数的名字和文档字符串，所以它决定的是调不调，至于调完之后去哪，不归它管。

### 2.4 破折号补语

> ✗ 如果程序员不写那个函数，AI 模型永远无法转交——它的工具列表里根本没有这个选项。
> ✓ 如果程序员不写那个函数，AI 模型就永远转交不了，因为它的工具列表里没有这个选项。

### 2.5 「一个……，一个……」的对称重复

> ✗ 一个管传，一个管存。
> ✓ 它们负责的事不一样。（然后分别展开）

### 2.6 带括号注解的排比

> ✗ 得看三件事：生命周期（活多久）、作用域（谁能看见）、持久化归谁管（谁负责在运行结束后把它留下来）。
> ✓ 关键还是看这份数据能活多久、谁能看见它，以及运行结束后由谁负责把它留下来。

### 2.7 「翻译一下」式回述

先贴代码、再用大白话把同一件事重述一遍，这种写法不要。

> ✗ 翻译一下：你这个工具函数的参数列表里如果写了 `context_variables`，Swarm 就把当前上下文塞进去；没写就不塞。
> ✓ 工具函数如果需要上下文，在参数里写上 `context_variables` 就行，Swarm 会自动传进去。

同理，`也就是说`、`换句话说`、`简单来说`、`说白了就是`、`一句话`、`一句话总结` 这类收口词默认都不用，要点直接说。

### 2.8 段落之间的阶段性总结与回指

> ✗ 到这儿第一部分可以收一下了。……记住这三者各自的职责，后面就不会绕晕了。
> ✗ 角色分清了，再回头看这个上下文变量。
> ✗ 到这儿，可以正面回答最开始那个问题了。
> ✗ 回到最开始那几个问题：1. …… 2. …… 3. ……
> ✗ 所以更准确的说法是：……（表格里已经写清楚了）

说完一个点直接进下一个。段落末尾不需要向读者汇报"我们现在讲到哪了"。

章末确实需要收束时，参考第二章的做法：用一张脉络表加「下一步可以玩什么」清单，不要用叙述式复述。

### 2.9 拿整句话当小节标题

> ✗ `## 2. 我前面有句话说得不对`
> ✓ `## 2. 纠错（I'm Sorry）`

> ✗ `:::important 这是这一篇里我最想纠正的一点`
> ✓ `:::important 真正的差别`

标题是索引，不是结论。用短标签或短问句。

## 3. 可以用的、推荐的写法

- **表格**：只在需要并排对比时用。前两章本身就有几十行表格，不存在"表格太多"的问题。
- **`:::note` / `:::tip` / `:::important`**：用来装要点，标题写短标签。
- **把读者的疑问写出来**：`可能你会想：……`。这类假设性提问是受欢迎的写法，用它替代 FAQ 式面板。
- **展开过的类比**：像第二章「你跟朋友约定说'开始'」那样讲完整，不要压缩。
- **代码块加一句直接解释**：解释放在代码后面，语气平实，不加"翻译一下"之类的提示词。
- **自嘲式的纠错**：发现自己前面说错了，直接写出来（`## 2. 纠错（I'm Sorry）`），不要用"这里我自己被打脸过一次"这类表演性说法。

## 4. 提交前自检

写完把下面的命令跑一遍，期望输出全部为 0：

```bash
p="src/content/posts/<slug>/index.md"
for k in "，也" "也不会" "——" "关键在于" "说白了" "也就是说" \
         "换句话说" "简单来说" "翻译一下" "小结" "到这儿" \
         "回到最开始" "收一下" "记住这" "是一张" "管子" \
         "空箱子" "大脑" "打个比方" "站着" "而生"; do
  printf "%-12s %s\n" "$k" "$(grep -c "$k" "$p")"
done
```

补充说明：

- 上面这串关键词只覆盖已知的坏句式。**发现新的同族写法，追加到本文档第 2 节**，别只改那一篇文章。
- 最后按项目惯例跑一次 `astro build`，确认新增文章正常产出页面。
